# 全局规则

## 语言设置

始终使用中文回复用户。无论用户使用何种语言提问，都必须用中文进行思考回答和交流。

此规则适用于所有会话,无论当前的工作目录和项目如何

## 权限受限设置

凡是遇到权限不足并且需要用户密码的情况,优先生成交互式权限确认脚本,并请求用户手动执行

## 文件检索与读取工具规范

- 查找文件:优先使用 `glob` 工具。
- 搜索文件内容:优先使用 `grep` 工具。
- 读取文件:优先使用 `read` 工具。
- 修改文件:优先使用 `edit`/`write` 工具。

## 代码改动规范

- 修改代码前先阅读相关文件与周边上下文,理解现有风格与约定,不要凭空假设。
- 在编写和修改代码时,插入适当对人类阅读友好的中文注释
- 遵循项目已有的命名与格式化习惯。
- 不要主动执行 `git push`,除非用户明确要求。

## 文件改动汇报

- 不得静默修改文件:每次调用 `edit`/`write`/`patch` 等落盘工具前,先用一句话说明「改哪个文件、改什么」,禁止连续落盘却没有任何说明。
- 每段回复的最后固定输出「### 文件变更」小结,逐条列出本轮实际落盘改动,格式为「动作 + 文件路径 + 一句话改动点」:
  - `新增`:`path/to/file` —— 用途
  - `修改`:`path/to/file` —— 改了什么(一句话概括,不粘贴完整 diff)
  - `删除`:`path/to/file` —— 删除原因
  - 本轮没有任何文件改动时,明确写「本次无文件改动」,不要省略该小结。
- 通过 `shell` 间接写入的文件(重定向、`sed -i`、`tee`、脚本生成等)同样计入。
- 子代理或后台任务产生的文件改动,主代理汇总时并入同一清单。
- 只读操作(读取、搜索、运行测试)不计入清单。

## 提交信息规范

- 提交信息遵循 Conventional Commits 格式:`feat:` / `fix:` / `refactor:` / `docs:` / `chore:` / `test:` / `perf:`。
- 提交信息使用中文描述改动内容。

## 验证要求

- 完成任务后,尽可能运行测试验证改动是否通过。
- 优先使用项目提供的测试方法

## 交互原则

- 回答保持简洁、直接。
- 遇到需要用户决策的选择点时,优先使用提问工具让用户拍板,而不是自作主张。
